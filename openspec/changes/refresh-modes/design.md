# Design

## Context

See proposal.md (Why). The current pipeline is one GitHub Actions workflow. `refresh.yml` runs a `gate` job (`ffapp should-run`), then a `refresh` job: install, `pytest`, `ffapp refresh` (12 steps, 55 s measured locally), commit `data/` and `site/data/`, `stamp-site`, Pages deploy. The relay (`relay/worker.js`) only dispatches that workflow, with a 15-minute cooldown. The page polls `data/index.json` once a minute.

Measured step times: sync 17.8 s, export 7.4, snapshot 6.3, stats 4.2, projections 4.0, games 3.7, simulate 3.2, war 2.9, replacement 2.2, ratings 2.1, schedule 0.9, trending 0.5. The work is small; the delay is runner setup, the test suite and the Pages deploy.

Constraints:
- Cloudflare free plan: 1,000 KV writes a day, 100,000 requests and KV reads a day, and too little CPU per request for the simulation.
- GitHub: the cron minimum is 5 minutes and runs are often late; Pages soft limit of about 10 deploys an hour; the API allows 5,000 requests an hour per token.
- Sleeper: under 1,000 calls a minute.

The full design, as readers will see it, is drafted in `docs/refresh-modes.md`, with its diagram generated by `tools/refresh_modes_diagram.py`.

## Goals / Non-Goals

**Goals:**
- A button press shows new data in about 1 to 1.5 minutes in Quiet.
- A live score shows up on an open page within about 2 minutes.
- No commit unless a record changed; no deploy unless the site changed.
- Every data path belongs to a documented tier, enforced by a test.

**Non-Goals:**
- Rewriting existing git history to shrink the repository.
- Moving the simulation or the cold run off GitHub Actions.
- In-game player projections (a separate backlog item; the hot run uses the same model as today).
- Paid Cloudflare or GitHub plans.

## Decisions

### 1. The Worker is the clock; GitHub Actions does the work
A Cloudflare cron trigger (`* * * * *`) runs the Worker's scheduled handler every minute. It reads the schedule summary and the bundle's game status from KV, works out the mode, and dispatches `hot.yml` or `refresh.yml` when due.

- **Alternative: GitHub cron.** Its 5-minute minimum and frequent delays can't give back-to-back hot runs.
- **Alternative: run the simulation in the Worker.** The free plan's CPU limit is far too small for 10,000 runs.

GitHub's own `0 11 * * *` schedule stays on `refresh.yml` as the fallback.

### 2. Mode logic lives in JavaScript, fed by Python
`mode(now, summary, bundleStatus)` is a pure function in `relay/worker.js`, tested in `worker.test.mjs`. The cold run's schedule step writes the summary to KV with `PUT /schedule`:
- each game's kickoff time and slate;
- whether each league's season is over;
- the NFL state's week.

The summary is small and changes rarely, so it costs about one write per cold run. To save writes, the cold run skips the write when the summary is unchanged (it compares a hash it stores in the build cache).

- **Alternative: the Worker calls ESPN or Sleeper itself.** That spreads data fetching across two codebases.

### 3. "Is a hot run going?" comes from GitHub, plus the Worker's memory
The Worker lists `hot.yml` runs with status `queued` or `in_progress`, as the cooldown already does for `refresh.yml`. It also remembers its last dispatch for 60 seconds, because a new run takes a few seconds to appear in the list. That's one API call a minute in Live, and none when nothing is due.

### 4. The hot run is a separate workflow and command
`hot.yml` is one job with its own concurrency group (`hot`, `cancel-in-progress: false`) and no `pages` or `contents: write` permission. Its steps:
1. checkout;
2. setup-python with the pip cache;
3. `pip install -e .`;
4. restore the build cache;
5. `python -m ffapp hot`;
6. `curl PUT /live` with `HOT_TOKEN`.

`ffapp hot` does the following:
- reuses the existing pieces: `sync` limited to current-week matchups, the scoreboard schedule step, `simulate` and `games`;
- writes into a scratch folder, never `data/`;
- exports only the league forecast files and the current-week game files, into one JSON bundle (`live.json` in the job's temp folder).

The bundle's schema: `{ generated_at, base_commit, mode_status: { games: {id: "pre|in|final"} }, leagues: { <key>: { forecast: <site/data/<key>.json>, games_week: N, games: <site/data/<key>/games/week_NN.json> } } }`. The page swaps those two files exactly as it would swap deployed ones.

- **Alternative: one KV key per file.** About 1,800 writes on a Sunday, over the free limit.

### 5. The build cache carries derived data between runs
At the end of a cold run, `actions/cache/save` stores `data/ratings`, `data/replacement`, `data/war`, future-week projections, the game files' derived parts and `site/data`, keyed `build-<run id>-<attempt>` (cache keys cannot be overwritten, and several runs can start from the same commit). Hot runs, the next cold run and `site.yml` restore with `restore-keys: build-`, so they get the newest cache on `main`.

When there is no cache, `ffapp build` regenerates everything offline:
- ratings, replacement and WAR from committed data;
- game views and baseline from the log;
- the export.

Future-week projections can't be rebuilt offline, so the simulation then uses the latest committed week's projections for later weeks and logs that it did.

- **Alternative: commit derived data, but only on change.** WAR, projections and games change on nearly every run, so this saves little.
- **Alternative: upload a workflow artifact.** Artifacts are per run and need an API lookup to find the latest; the cache restores by prefix in one step.

### 6. Splitting the game file
`data/games/<league>/<season>/week_NN.json` keeps `log`, `record`, `league_key`, `season` and `week`. The derived parts (`forecast`, `views` and `baseline`) move to `data/games-derived/<league>/<season>/week_NN.json`, which is git-ignored and in the build cache.

`Store.read_games` merges the two, so readers stay unchanged. `write_games` splits them. The record part is written only when it changed, using the same `same_entry` comparison the log already uses.

### 7. The last-run time leaves git
`data/refresh/last_run.json` becomes a git-ignored file in the build cache. The export already reads it for `index.last_refresh`. The page's "Updated" time becomes the newer of `index.last_refresh` and the bundle's `generated_at`.

### 8. Commit and deploy only on change
The cold run runs `git add` on the tracked record paths. When `git diff --cached --quiet` reports no change, there is no commit. For the deploy, the run hashes `site/` with `generated_at` and `last_refresh` stripped (a small `ffapp site-hash` helper) and compares it with the hash saved in the previous build cache. The deploy steps run only when a commit was made or the hash differs.

### 9. Tests move out of the data refresh
`pytest` leaves `refresh.yml`. It still runs on every push that changes code (`site.yml`), which is where code can break. Data-shape problems surface as a failed step in `ffapp refresh` or `ffapp build`, which already fail the run without committing. This saves about 1 to 2 minutes per cold run.

### 10. The page reads the bundle from the relay
`updates.js` gains `fetchLive()`, which calls `GET <refresh_url>/live` with no-store.
- **Interval:** 30 s when the last bundle's status shows a game `in` progress, 60 s otherwise.
- **Swap rule:** when `bundle.generated_at` is newer than both the loaded static `last_refresh` and the last bundle, the page hands the bundle's files to the same reload hook as deployed data.
- **Loader:** `fetchJson` paths for `data/<key>.json` and `data/<key>/games/week_NN.json` check an in-memory overlay first, so every page view, including week switches, sees the bundle's version.

### 11. Button behaviour comes from the relay
`GET /status` adds `mode` and `reason` (`live`, `running`, `cooldown`), and the page picks the note from them. `POST /refresh` dispatches by mode: `hot.yml` and `refresh.yml` in Quiet, `refresh.yml` in the off-season, and 409 `{reason: "live"}` in Live. The notes "Live updates on" and "Started, back in ~1 min", and their tooltips, get copy IDs.

### 12. Tallies are committed once a day
The first Quiet hours on the new pipeline committed on 18 of 19 cold runs. Two causes:
- Sleeper bumps `last_modified` on projections without changing values. The merge now replaces a record only when something besides that time changed.
- Trending counts and ESPN rostered and started percentages change on every fetch.

For the tallies, the run still writes the files, so the export and site carry the latest values. After `git add data`, `ffapp hold-tallies` unstages and restores each changed tally file whose committed copy was saved on the same UTC day (its `saved_at` or `captured_at`). A new file, such as the day's first trending file, is kept. So git gets one copy a day, from the first cold run after midnight UTC.

- **Alternative: a derived live copy for tallies.** Every reader would have to look in two places.

## Risks / Trade-offs

- **Two sources of truth on the page (bundle and static files)** → One swap rule (newest wins), one overlay in the loader, and a layout test that serves an older and a newer bundle.
- **KV writes exceed 1,000 on an unusual day (for example, the day after Thanksgiving with many games and many button presses)** → The bundle write is skipped when its content hash matches the previous bundle (no scores changed). The Worker counts writes per UTC day and stops dispatching hot runs at 950. Cold runs carry on.
- **The GitHub token's API budget** → The run list is called only when a run is due. About 60 calls an hour at most, against a limit of 5,000.
- **The build cache is evicted, or one was never written** → `ffapp build` offline fallback; the hot run takes about 20 s longer (18 s measured).
- **A stale game status keeps the site in Live** → The 6-hours-after-kickoff rule; Live ends at the latest 6 hours after the last kickoff.
- **Local workflow change: `site/data` is not in git** → `ffapp build` documented in the README and in `docs/refresh-modes.md`. The layout tests build the site data first (a session fixture runs `ffapp build` when `site/data` is missing).
- **The Worker's clock silently stops** → GitHub's daily cold run; the page's "Updated N h ago" makes staleness visible.
- **Removing the gate loses the ESPN and schedule failure annotation** → Unchanged: those live in `ffapp refresh` (the optional steps), not in the gate.

## Migration Plan

1. Land the code with the Worker's clock disabled (no cron trigger yet). `refresh.yml` keeps its hourly cron during this step. A first cold run on the new code writes the build cache and schedule summary.
2. Create the KV namespace and set `HOT_TOKEN` in Cloudflare and GitHub. Deploy the Worker with `wrangler deploy`; the owner runs it, since the credential is theirs. Run `hot.yml` by hand once and confirm the page swaps the bundle.
3. Enable the Worker's cron trigger and remove `refresh.yml`'s hourly cron, keeping the daily one.
4. Untrack the derived paths: `git rm -r --cached site/data data/war data/ratings data/replacement`, plus the future-week projection files, `live.json` and `last_run.json`. Add them to `.gitignore` in the same commit.

**Rollback:** remove the Worker's cron trigger and restore the hourly cron on `refresh.yml`. The page falls back to static files on its own when no newer bundle exists. Reverting the untracking commit brings derived files back into git on the next cold run.
