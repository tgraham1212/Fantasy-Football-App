# Design

## Context

See proposal.md for motivation. What exists today:

- `data/leagues/<league>/<season>/` holds `rosters.json` (end-of-season `roster_id` → `owner_id`), `users.json` (user_id → display_name) and `matchups/week_NN.json` (points per roster per week). `regular_season_range(league)` in `ffapp.odds` gives the regular-season weeks; `settings.last_scored_leg` says which weeks are final.
- `ffapp.export` already emits `elo: null` and `elo_change: null` per team; `site/app.js` renders both columns, with `.elo-delta.up/.down` pill styles in place and the two headers excluded from sorting.
- The odds chart uses `--team-1..12` CSS tokens assigned by ascending `roster_id`, generated by `tools/team_palette.py` and validated with the dataviz palette validator; direct labels at line ends are drawn by a Chart.js plugin.
- The spike over the stored seasons (dynasty 2022–2026, redraft 2021–2026) established the parameter choices recorded below; its scripts live outside the repo.
- `config.py` rejects unknown keys per block; `_SIMULATION_KEYS` is the pattern to copy for a `ratings` block.

## Goals / Non-Goals

**Goals:**
- A rating pipeline that is deterministic, cheap (seconds), and re-runs over all seasons every refresh so a corrected matchup or a re-synced roster is reflected without state.
- Parameters that are explicit config with defaults chosen from roster facts, applied identically to both leagues.
- A chart that reuses the odds chart's machinery (Chart.js, team tokens, direct-label plugin, highlight state) rather than a second implementation.

**Non-Goals:**
- Feeding ratings into the simulation. The background variants are stored for a later calibration experiment.
- Head-to-head records, luck metrics or all-play records (future "owner stats").
- Historical mid-season ownership. Sleeper exposes end-of-season owners only.

## Decisions

**Openskill Plackett-Luce on a native 1000 scale.** `PlackettLuce(mu=1000, sigma=1000/3, beta=1000/6, tau=1000/300)` is the library's default model with every parameter multiplied by 40, so the ratings are already on the familiar scale and need no display transform. `rate(teams, scores=[...])` with one single-player team per roster ranks the week; higher score wins (verified). Alternative: Elo with pairwise all-play updates. Rejected because Elo is zero-sum, which is the direct cause of the inflation the user asked about, and because it needs a hand-made multiplayer extension.

**Reversion toward a fixed 1000, fraction 1/3, both leagues.** The spike showed dynasty inflating from 1003 to 1138 with no reversion as weaker members left; anchoring to 1000 held it at 1030–1060. Redraft accuracy is slightly better with a full reset, but the user wants a continuous career rating in both leagues; 1/3 keeps it continuous while bounding drift. Sigma is left alone: a preseason sigma reset sped up every week of the season because `tau` keeps sigma near 240 anyway, and widened the spread.

**Early-season multiplier applied to the mean delta.** After each `rate()` call in rated week `i` (1-based within the season), `mu = mu_prev + k_i · (mu_new − mu_prev)` with `k = [2, 1.75, 1.5, 1.25]` and 1 afterwards; sigma takes the model's value. Measured: doubles week-1 movement, week 4 at 64 vs week 5 at 51, no accuracy change, end spread 339 vs 293. Alternatives: lowering `beta` for early weeks (only +12%), inflating sigma (not targeted). This is the one step outside pure Openskill, so it is isolated in one function and documented in the config comment.

**Identity = Sleeper user_id from that season's `rosters.json`.** Display name = the latest `users.json` entry that has the user (former members keep the name from their last season). A roster with `owner_id` null is rated under `vacant:<season>:<roster_id>` with `vacant: true`; it participates in the week's ranking and is excluded from the export's chart list. Co-owners are not present in either league; the primary `owner_id` would be used if they appeared.

**Z-score with sample standard deviation.** `z = (pts − mean) / std(ddof=1)` over all teams that week (vacant included). Career mean z is a running mean over all rated weeks. Background variants: season-to-date mean z (reset at season start), EWMA z with weight 0.2 carried across seasons, and a fresh-start Openskill run (`revert=1`, no multiplier). All four series live in the same history entry.

**File layout** `data/ratings/<league>.json`:

```
{league_key, generated_at, parameters: {...},
 seasons: ["2022", ...],
 managers: {<user_id>: {display_name, current: bool, vacant: bool,
                        seasons: [...],
                        history: [{season, week, mu, sigma, z, career_z,
                                   season_z, ewma_z, fresh_mu}, ...]}}}
```

`history` entries hold the values *after* that week's update, so the last entry is the current rating. The export derives `elo` = last `mu` rounded, `elo_change` = last `mu` − previous entry's `mu` (null with fewer than two entries), and attaches `ratings: {weeks: [{season, week}], managers: {id: {display_name, current, roster_id|null, mu: [...], career_z: [...]}}}` aligned to the league-wide week list with nulls where a manager did not play. Vacant entries are dropped from the export.

**Refresh order** sync → projections → stats → ratings → replacement → simulate → export. Ratings need only matchups and rosters, so they sit right after the data they depend on and before the slower steps.

**Chart.** A second `<canvas>` under the odds chart, driven by the same `renderChart`-style function parameterised by series and the same direct-label plugin. The x-axis is the league-wide week list with category labels `"2022 wk1"`, ticks thinned to show season starts (first rated week of each season) and a vertical grid line at each boundary. The metric switcher reuses the pill markup; the range switcher is a second pill row with `This season | Last 3 seasons | All time`, implemented by slicing the week list (no re-fetch). Highlight state is shared with the table and odds chart (`state.selected` keyed by roster_id for current members; former members use their user id and only highlight within the rating chart).

**Colours.** Current members map user_id → current roster_id → existing `--team-N`. Former members get `--former-1..6`: six greys spaced in OKLCH lightness per theme, generated by a new `--greys` mode in `tools/team_palette.py` and checked with the dataviz validator for normal-vision separation and contrast against each surface (the CVD check is moot for neutrals). Six covers dynasty's five former managers with one spare; a seventh and beyond would reuse the darkest grey, which is acceptable for history lines. Alternative: hues for former members. Rejected: 17 separable hues do not pass the validator and would clash with current members.

**Config.** `ratings:` block with keys `revert` (0..1, default 1/3), `early_k` (non-empty list of numbers ≥ 1, non-increasing, default [2, 1.75, 1.5, 1.25]), `start_mu` (default 1000), `start_sigma` (default start_mu/3), `ewma_weight` (0 < w ≤ 1, default 0.2). Parsed like `simulation`, unknown keys rejected, parameters echoed into the rating file.

## Risks / Trade-offs

- [Openskill API changes] → pin `openskill>=6.2,<7` in `pyproject.toml`; the only calls used are the constructor, `rating()` and `rate(scores=)`.
- [Rating file grows each week] → about 17 managers × 70 weeks × 9 numbers per league; tens of kilobytes. The site file carries only two series.
- [Mid-season owner changes attributed to the end-of-season owner] → documented limitation on the page's hint text; the vacant mechanism keeps the ranking complete.
- [Former-member greys hard to tell apart on a dense chart] → direct labels at line ends plus hover tooltips name every line; highlighting isolates one.
- [Regular-season weeks include a bye-ridden week 14 in some seasons] → same treatment as every other week; the model has no notion of lineup strength, only rank.
- [The multiplier makes the rating step outside Openskill's Bayesian update] → confined to one function, schedule in config, documented in the file's `parameters`.

## Migration Plan

1. Add the dependency and the `ratings` command; run it once locally to produce the two files and commit them with the code.
2. Export and site changes ship in the same commit; the site handles a missing `ratings` block, so a partial deploy degrades to today's empty columns.
3. The daily workflow picks up the new refresh step automatically; no secrets or workflow edits beyond the dependency install already using `pip install -e .`.
4. Rollback: revert the commit; the rating files are derived data and can be deleted or regenerated at any time.
